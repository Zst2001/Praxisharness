# Harness 三组实验说明

目标：在相同模型、任务和预算下，比较基础执行、只做验收以及验收后有限修复的效果与开销。实验结果属于固定本地任务集，不代表任何公开排行榜成绩。

## 任务集

默认 `benchmarks/harness_suite_v2.json` 包含四类任务，每类 3 题：

| 类别 | 任务 |
| --- | --- |
| 配置处理 | 配置类型与字段、重试参数、布尔特性筛选 |
| 数据处理 | 数值汇总、去重排序、CSV 订单聚合 |
| 代码修复 | slugify、数值边界、保持顺序的去重 |
| 多文件一致性 | 发布版本同步、双格式报告、记录拆分 |

这是小型工程实验集。需求来自清单中的显式说明，初始文件与独立评分固定。Python 题有公开测试及额外行为测试；评分还检查不应被修改的输入和公开测试文件是否保留。题目和脚本答案由项目维护者编写，不能用于声称模型在未知公开基准上的泛化水平。

## 实验控制

| 组 | 运行期策略 |
| --- | --- |
| baseline | 基础工具循环，最终回答后直接退出 |
| verify | 执行最终验收，不允许自动修复 |
| repair | 验收失败后提供结构化反馈，在预算内修复 |

所有组获得相同的任务文本与公开条件。两种验收组另由 Runtime 注入验收状态与反馈，这是所比较策略的一部分。每次执行使用独立目录和实例，三组循环轮换顺序。模型决策预算在共同的 Runtime 入口检查，超限决策不会发起模型请求；内部 transport / 输出格式重试仍按原有机制计数，实际请求次数另外报告。

固定模型配置、输出上限、temperature、重试设置和任务集。报告记录清单哈希、逐题公开提示哈希、配置模型名及最后一次返回的模型标识。模型名可能是服务别名，正式实验需另确认服务版本；不存在可用标识时不能假定服务未变化。

## 独立评分

公开条件用于指导执行和触发修复。`rubric` 仅用于任务退出后的评分，真实模型和工具在执行期间不会获得其内容，也不会获得 `demo_outputs`。

文件评分使用 JSON 值匹配、完整文件字节匹配和输入保留检查，均保持路径边界和有界读取。Python 评分脚本在任务结束后生成于工作区外，使用只读沙箱调用提交代码，检查返回结果和输入未被修改，并要求评分器实际完成。没有健康 Broker 时返回 `blocked`；不自动安装 Broker，不执行宿主兜底。

评分脚本与提交代码仍在同一沙箱进程内执行。这是普通行为测试，不是能够抵御任意恶意提交代码的独立裁判服务；有意攻击评分器的任务需要更强隔离和额外审计。本实验不将此机制表述为抗作弊基准。

## 运行与产物

```powershell
# 免费流程演示，不调用模型
uv run python -m benchmarks.harness --repeat 3

# 显式调用配置的服务；调用前确定模型与预算
uv run python -m benchmarks.harness --config C:\path\to\model.toml --repeat 3 --output benchmarks/output/model-experiment.json
```

输出包含：

- `.json`：逐项执行、独立评分、预算、Token、修复历史和配对结果。
- `.md`：三组完成率、耗时、Token 及结果分类汇总。
- `.trials.jsonl`：首行实验元数据，后续逐次结果立即刷新；中断后可检查已完成的结果，不提供自动续跑。

`mode=scripted_demo` 表示刻意提前结束再根据反馈写入答案的规划器，只用于流程验证。`mode=llm` 表示调用了配置服务。报告固定 `capability_score=false`：无论使用何种服务，该本地实验都不作为官方能力成绩。未经配置和费用预算确认，本项目的自动验证只使用 loopback 模型服务。

## 指标口径

schema version 7 新增 `budget_finish_v1`：两组获得相同初始公开反馈，分别预留 0/2 次工具额度，比较同总额下的收尾策略。记录阶段预算、收尾原因和重复参数动作计数，见 [本阶段实现](harness-budget-finish.md)。

schema version 6 增加 `retry_feedback_v1` 两组等机会复查协议、共同初始公开证据、资源等待摘要和命令启动/轮询/stdin 分项计数；配对比较明确 `reference_arm`。费用在原账本上增加不可重置的实验子预算。设计、真实结果与版本边界见 [本阶段记录](harness-feedback-control.md)。

schema version 5 增加逐轮快照、修复开销和 case 状态迁移，以及独立标记的固定候选条件修复协议，见 [本轮实现](harness-rounds-validation.md)。`independently_failed_repair_trials` 只统计首轮独立失败且确实分配了反馈修复的 trial；`independently_repaired_successes` 还要求最终运行完成且独立评分通过。预算中断但产物通过不计为执行成功；新引入的失败按相邻快照或最后快照到最终产物的 case 状态迁移统计。

schema version 4 新增候选证据、逐 case 结论、公开输入指纹与工具阶段摘要，见 [证据及 V2 验证](harness-evidence-validation.md)。公开检查版本变化必须保留不同套件指纹，不与旧报告混算；独立 rubric 未变也不等于两轮试验条件完全相同。

schema version 3 起，Token 来自 trial 全部请求尝试的 Provider 用量累计，Token 均值仅统计用量完整的 trial，另报未知用量数量；本地估算单独保存。旧版真实试跑的 Token 均值只取最后一次响应，不能用于比较整次任务的消耗。原始历史报告不回填或改写。新增代码集和请求关联说明见 [后续实现记录](harness-next-validation.md)。

- `pass_rate`：运行完成且独立评分通过的次数 / 全部执行次数，环境阻塞也计入分母。
- `artifact_pass_rate`：独立评分通过数 / 有明确通过或失败结论的评分数；同时报告 `graded_trials`，不把阻塞伪装成任务零分。
- `repaired_successes`：首次验收失败、最终执行完成且独立评分通过的次数。
- `false_acceptance_rate`：内部验收通过但独立评分失败的次数 / 内部验收通过次数；无内部通过项时为 null。
- 模型决策、实际请求、重试、工具调用及 Token 分别记录。服务没有报告 Token 时保留缺失值，不填充为零。
- 执行耗时与独立评分耗时分开。P50 为样本中位数，P95 为最近秩样本分位数。
- 配对结果逐题、逐次比较 baseline 与另外两组，保留双通过、单组通过与双失败数量。

先用少量真实调用检查配置与评分，再扩大重复次数。小样本应展示原始次数和失败案例，不据此宣称统计显著。真实模型实验可能出现无提升甚至下降，报告不预设修复组更优。

## 持续验证

正式实验前先运行 [本地预检与四题试跑](harness-recovery.md)。报告现包含同一实验 ID、实际选题和源码/依赖指纹；Git 尚无提交时不会伪造 commit 标识。当前机器的实际准入结果以最新 `preflight.json` 为准，不能只根据 Broker `healthy=true` 推定命令可用。

`.github/workflows/ci.yml` 在 Windows 执行锁文件安装、Ruff、默认后端测试、前端类型检查、测试和构建。该工作流未在本轮推送或触发远程运行。

受保护 Windows 对象的测试使用 `windows_admin` 标记，仅在真正提升的令牌下运行：

```powershell
uv run python -m pytest -q -m windows_admin
```

真实 Broker 隔离、Docker 和 MCP v1 测试沿用原有显式环境开关或独立环境，不因为缺少依赖而降低实现的保护条件。默认测试不能证明这些可选环境中的隔离能力。
