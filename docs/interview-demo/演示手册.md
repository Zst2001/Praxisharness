# Praxis Harness 面试演示

建议用 6～8 分钟展示一次完整任务，再按剩余时间展示修复证据和项目记忆。案例使用虚构订单，日期固定为 2026-11-08，面试当天无需调整。

本次已准备好的演示目录为 `F:\JavaProject\Praxis-interview-demo-gm9kl2n4`，保留初始错误，可直接在 Praxis 中新建项目并选择它。下面的准备命令用于额外创建排练副本。

## 你要演示的需求

“运营拿到一份订单数据和一份错误的日报，希望 Agent 按业务规则修正汇总，生成中文报告，并通过程序检查。”

输入共 7 条订单，有同一买家的重复订单、已取消订单、退款订单和前一天的订单。旧汇总错误地统计了全部订单，并把布尔值写成了字符串。

正确产物为 4 笔当日已支付订单、3 位买家、31000 分，即 310.00 元，以及布尔类型的 `ready`。

这套演示可说明文件工具、用户定义的验收契约、有限修复、逐轮证据和跨会话项目经验。主任务中的统计与文案仍由模型完成，现场调用配置的模型可能产生费用。

## 面试前准备

### 1. 创建独立的演示项目

在 PowerShell 中执行。每次会生成一个新文件夹，终端最后一行就是需要在 Praxis 中选择的项目路径。

```powershell
cd F:\JavaProject\Praxis-main
uv run python docs/interview-demo/demo.py prepare
```

目录类似 `F:\JavaProject\Praxis-interview-demo-xxxxxxxx`。其中只有 `TASK.md`、`data/orders.json` 和错误的 `daily-summary.json`，模型看不到手册与独立检查脚本。需要重新演练时，再执行一次上面的准备命令，并新建对应项目。

### 2. 启动与检查

```powershell
cd F:\JavaProject\Praxis-main
uv run python -m backend.api
```

保持终端打开，访问 <http://127.0.0.1:8000>。若后端已经在运行，直接打开页面。若界面提示 Broker 未启动，在管理员 PowerShell 执行以下命令，再检查页面上的沙箱状态。

```powershell
Start-Service PraxisSandboxBroker
Get-Service PraxisSandboxBroker
```

确认已配置的模型可用。打开「用户设置 → 记忆」，开启「启用记忆」，关闭「允许后台模型提取与整理」，本次只演示用户确认保存和本地检索。该设置有持久化效果，演示后可以按日常需要调回。使用远程模型时，检索命中的经验也会随当次对话请求发送。

先用一份独立项目完整排练一次。正常现场演示只需少量轮次，但验收中的“工具调用上限”不限制人民币费用。

## 现场主流程，约 4 分钟

### 1. 用 20 秒介绍项目

可以这样说：

> Praxis Harness 是一个围绕本地项目工作的 Agent 工作台。我给任务设置可执行的验收条件，系统会读取实际产物进行检查。失败时，检查结果进入下一轮模型上下文，并在修复次数和调用额度内继续执行。下面用一份有错误的订单日报展示整个过程。

### 2. 新建项目并展示输入

点击「新建项目」，选择准备命令输出的文件夹。在项目下新建对话，确认模式为「Agent」，权限为「工作区读写」。打开 `TASK.md`、`data/orders.json` 和旧版 `daily-summary.json`，指出旧汇总把取消、退款和其他日期也算进去了。

### 3. 配置验收

点击输入框上的「验收」，添加以下三个条件。`acceptance-main.json` 是便于核对的后端契约示例，当前页面通过表单逐项配置。

| 条件类型 | 路径 | 预期内容 |
| --- | --- | --- |
| JSON 内容匹配 | `daily-summary.json` | 粘贴下方完整 JSON |
| 包含指定文本 | `report.md` | `订单日报` |
| 包含指定文本 | `report.md` | `310.00 元` |

```json
{
  "date": "2026-11-08",
  "paid_orders": 4,
  "unique_buyers": 3,
  "total_amount_cents": 31000,
  "ready": true
}
```

最多修复次数设为 **2**。「高级限制」中工具调用总上限设为 **64**，预留验收调用次数设为 **0**，点击「应用」。三个文件条件直接读取文件，本例无需命令验收。

### 4. 发送下面的任务

```text
请阅读本项目的 TASK.md、data/orders.json 和 daily-summary.json。
按照 TASK.md 中的规则修复日报，并创建中文 report.md。
只修改 daily-summary.json 和 report.md，保留输入数据与任务说明。
这是一个小型文件处理任务，优先使用文件读写工具，无需安装依赖或访问网络。
完成后简要说明修正了哪些问题，并提交工作区产物供已配置的验收条件检查。
```

执行时展示文件读取、写入和模型回复。若出现审批，先查看具体操作，再按界面确认。用一句话解释权限范围。

### 5. 展示结果

展开「任务验收结果」，指出哪些条件通过，再打开两个输出文件。可以解释：

> 这里的 JSON 条件重新解析工作区文件，同时检查数值和类型。字符串 "true" 与布尔值 true 会得到不同结果。报告中的文字条件只证明指定内容存在，完整文案仍需要审阅。

可选地，在项目仓库根目录执行独立检查。把路径替换为当前演示项目路径。

```powershell
uv run python docs/interview-demo/demo.py verify "F:\JavaProject\Praxis-interview-demo-xxxxxxxx"
```

输出 `PASS` 表示汇总值和类型、报告必要内容以及原始输入完整性均满足检查。该命令由你在面试终端主动运行，检查脚本位于演示项目外。

若首轮就通过，可以直接说“这次一次完成，下面额外注入一个类型错误来展示修复路径”。已有错误文件被 Agent 一次修好，并不代表发生过 Harness 的失败复验。

## 修复与长期记忆，约 3 分钟

### 1. 在同一项目的新对话中配置一个条件

使用 Agent 和工作区读写权限。仅保留一个「JSON 内容匹配」条件，路径为 `repair-probe.json`，完整预期值为 `{"ready": true}`。修复次数为 **2**，工具调用上限为 **32**。对应的契约样例在 `acceptance-repair.json`。

在发送前向面试官说明“这一步是预先设计的故障注入，用来观察验收反馈是否确实触发修复”。然后发送：

```text
这是一个故障注入演示，分为首轮提交和收到验收反馈后的修复。
首轮请只将 repair-probe.json 写为 {"ready": "true"}，保留字符串类型，
然后直接提交最终回复“已提交首轮测试产物”，让运行时进行验收。
当你收到运行时的验收失败反馈后，再根据实际失败原因修正 repair-probe.json，
提交复验并说明类型差异。不要修改其他文件。
```

模型可能主动修正或不遵循分阶段要求，因此先排练。若它直接写对，现场如实展示首轮通过，转用排练时保存的真实失败记录或下面的免费流程测试。不要把两个独立任务中的失败和成功描述成一次自动修复循环。

### 2. 查看证据并保存经验

出现同一条件“第一轮失败 → 第二轮通过”后，在「任务验收结果 → 最新检查」点击「追踪修复」。展示失败详情、期间的文件写入操作、下一轮通过结果。报告可以下载留档。

点击「保存为项目经验」，填写下面两项。

**适用情形**

```text
本项目生成 JSON 状态配置时，ready 等开关字段要求为布尔类型，JSON 内容匹配验收提示类型不一致。
```

**建议做法**

```text
将 ready 写为不带引号的 true，避免使用字符串 "true"。修改后重新执行 JSON 内容匹配验收，核对实际文件的字段类型与预期一致。
```

点击确认。只有有项目绑定且同一条件有相邻失败与通过证据时，保存入口才满足要求。

### 3. 换新会话召回

仍在同一个项目下新建对话，确认关闭新任务验收，避免把旧的文件条件带到纯问答中。然后输入：

```text
本项目生成 JSON 状态配置时，ready 字段的布尔类型有什么注意事项？
请优先参考本项目已经保存的经验，若有命中，说明其历史来源和适用条件。
```

接着到「用户设置 → 记忆」选择当前项目，试搜“JSON ready 布尔类型”，展示条目和原始验收证据。检索命中由项目范围、文本相关性和上下文预算共同决定。能在设置页找到条目可以证明保存和检索；判断新会话是否实际使用，还应查看该次请求的上下文或可用的记忆记录，模型口头声称“记得”不足以单独证明注入。

可以这样讲：

> 这条经验保存了适用条件、建议做法和原始验收来源。后续会话会按项目范围检索并注入相关经验，新的任务仍需要重新验证。

## 现场备用方案

| 情况 | 处理方式 |
| --- | --- |
| 模型网络慢、报限流或运行超过 90 秒 | 查看运行状态，必要时停止任务。切换到排练留下的真实报告和产物，说明它们是提前录制或保存的结果。 |
| 沙箱状态异常或权限审批阻塞 | 展示具体错误与任务停止原因。用管理员终端启动 Broker 并确认就绪，仍异常时使用离线材料。 |
| 首轮直接通过 | 展示正常任务结果，再使用明确标注的故障注入补充步骤。 |
| 经验未召回 | 在记忆设置检查项目、启用状态和试搜结果。只有通过来源校验的记录才可保存。 |
| 被问及此前 GitHub CI 红叉 | 如实说明已有权限前提、中文编码、服务恢复测试问题，当前尚未完成这三项修复。演示预检覆盖范围见本目录的验证记录。 |

模型不可用时，可以在仓库根目录运行已有的免费修复流程回归。它使用本地脚本规划器，验证真实文件从缺失到修复通过，以及运行状态往返序列化。

```powershell
uv run python -m pytest -q tests/test_acceptance.py::test_failure_feedback_repairs_real_file_and_roundtrips_state
```

要清楚说明这是确定性流程测试。它不衡量真实模型能力，也不会在浏览器里自动生成一条可保存的项目经验。

## 面试时的讲解重点

- **Harness 的作用**。用户定义验收条件，运行时读取产物并检查，把失败结果交回模型，再按额度决定是否继续。
- **停止条件**。修复次数、模型轮数和工具调用次数限制执行。权限拒绝和沙箱不可用会形成阻塞。
- **可追溯性**。条件 ID 关联相邻轮次，工具调用记录说明中间做了什么，保存经验还会核对会话、Turn 和版本。
- **长期记忆**。SQLite 存储条目和证据，FTS5 配合汉字双字索引检索，按项目隔离并限制注入预算。
- **当前边界**。所选验收条件决定能证明多少，用户确认的经验也需要在新任务中重新验证。界面和本地数据位于本机，模型可连接远程服务。

今晚排练后，保留实际产物、验收 JSON 报告和关键页面截图。现场展示完整的一次任务，通常比临时安装依赖或切换多个模型更容易控制时间。
